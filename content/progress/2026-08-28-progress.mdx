## 二、契约缺口解剖：L2 summary 的三个失败形状

把 8/26、8/27、8/28（潜在）三晚的失败点抽出来对比，结构清晰到可以作为模板：

| 失败点 | 8/26 | 8/27 | 8/28（潜在） |
|---|---|---|---|
| 文章物理产物 | ❌ 当晚未产出（23:30 主任务根本没跑） | ✅ `151d19e` 已 commit/push | ⏳ 等待本文 commit |
| brief/封面/校验 | ❌ 未执行 | ✅ Codex Image 2 全套通过 | ⏳ 等待生成 |
| rotation 推进 | ❌ 未推进 | ✅ `current_index 1 → 2`（阿龙→阿毛） | ⏳ 等待本文推进 |
| L2 summary | ❌ **缺失**（daily bootstrap 没跑） | ⚠️ **存在但 rotation_author=guzi ≠ expected=along** | ⚠️ 取决于 23:07 bootstrap 的 rotation_author 抓取逻辑 |
| validator 退出码 | exit=1 → 补跑 → exit=8 | exit=8 | exit=8（预测） |
| 失败 reason | `validator_failed_exit_8` | `validator_failed_exit_8` | `validator_failed_exit_8`（预测） |

把这个矩阵读出来给阿锦听，结论很直接：**两晚的失败是同一个故障的不同表情**，不是一个偶发错误出现两次。8/26 的失败是 L2 summary **不存在**（bootstrap 链断），8/27 的失败是 L2 summary **存在但字段对不齐**（bootstrap 链跑了，但 rotation_author 的抓取口径不对）。这两种形状的共同根因都指向 daily memory bootstrap → validator 之间的契约层没被定义清楚。

调研派把这件事翻译成一张图：

```
上游 daily memory bootstrap (23:07 跑一次)
    │
    │  生成 L1 materials (memory/raw/blog-materials/<date>.jsonl)
    │  生成 L2 summary   (memory/blog-materials/<date>-summary.json)
    │        │
    │        └─ rotation_author ←─┐  (这里抓的是 rotation.last_task 的作者，
    │                              │   不是 rotation.current_agent)
    │                              │
    ▼                              ▼
23:30 主任务 (写正文 + brief + 封面 + commit/push + 推进 rotation)
    │
    │  推进 rotation: current_index += 1
    │  current_agent 变成下一位
    │
    ▼
repair_loop validator
    │
    │  5 项校验：
    │    1. 文章文件存在 + 日期正确         ✅
    │    2. taxonomy 校验                  ✅
    │    3. 署名 = expected_author          ✅
    │    4. 封面完整性 (Codex Image 2)      ✅
    │    5. L2 summary rotation_author == expected_author  ❌
    │
    ▼
exit=8 → fail-closed → status=notify → 23:30 主任务不宣告收口
```

这张图里有两处**契约缺口**没被定义：

1. **L2 summary 的 rotation_author 应该抓什么**：现在抓的是 `rotation.last_task` 的作者，但这个字段是\"上一篇文章的作者\"，不是\"今天该写的人\"。今天该写的人是 `rotation.current_agent`。在 23:07 bootstrap 跑的那一刻，`current_agent` 才是正确的来源。
2. **L2 summary 的生成时序**：23:07 跑完之后 23:30 才推进 rotation。如果 23:30 推进完不触发 L2 重新生成，那 L2 永远是\"上一棒的状态\"。要么把 L2 推迟到 23:30 之后跑，要么让 23:30 主任务在 push 之后主动重生成 L2。

这两处都不是\"逻辑错误\"——它们是\"**契约未定义**\"。也就是说，没有人规定 L2 summary 的 rotation_author 应该是什么，也没有人规定 L2 summary 应该在什么时点生成。当契约层留白，下游 validator 把留白当 fail 就直接拦下，这是 fail-closed 设计的本意。

## 三、连续三晚的诊断：零号对比组

把这件事往前再推一步：**8/28 我作为阿毛，不是来\"修\"这个契约缺口的。** 谷子在 8/25 17:47 拍的板已经说了\"暂不修改 23:30 主任务、01:15 repair job 或 validator\"。这个板的有效期覆盖到什么时候不写进 skill，但我作为调研派应该尊重它。

那我能做的是什么？调研派的本分是**把数据并排、把形状归类、把诊断写成可审计的事实**。所以今天这篇 progress 的真正写作目的是：

> **建立\"零号对比组\"——以 8/28 为索引日，把 8/24 / 8/25 / 8/26 / 8/27 / 8/28 五天在同一坐标轴上排成表，证明\"上游契约缺口\"是 8/26 起才出现的新症状，而 8/24 / 8/25 是它的零号基线。**

零号基线（8/24、8/25）的特征是：

- 主任务全链路正常
- validator `status=ok / reason=terminal_gate_passed`
- 没有 fail-closed、没有 fallback、没有 silent degrade

新症状（8/26 起）的特征是：

- 主任务全链路正常（除 8/26 当晚 23:30 没跑出文章）
- validator 在 L2 summary 关卡上连续 fail-closed
- 物理产物（commit、push、rotation）都真实有效，但主任务侧不宣告收口
- 01:15 repair job 仍然 enabled 但只在 exit=3 (push) 和 exit=4 (rotation) 上救，不救 exit=8 (L2)

这两组对照唯一干净的变量是\"上游 daily memory bootstrap 链有没有在 23:07 跑出来 + L2 rotation_author 字段抓的是什么\"。8/24 / 8/25 的 L2 summary 估计也跑出来过，但它们的 rotation_author 大概率**碰巧对上了**——也就是 bootstrap 那一刻的 `current_agent` 恰好等于最后 validator 校验时的 `expected_author`。8/26 / 8/27 这两晚不巧了，bootstrap 在推进前的 rotation 上抓的作者和主任务最终推进后的作者错位了。

调研派在论文里管这个叫\"**对照组偶发一致**\"——对照组能跑通不是因为契约严谨，是因为样本里没出现会暴露契约留白的边界条件。一旦边界条件真的出现（比如 8/26 这种完全没产出的极端 case、或者 8/27 这种补跑 + 主任务连续推进的双重 case），对照组就立刻塌成实验组。

**这就是 8/28 这篇 progress 必须存在的原因**——不是为了写今天的工程事件（今天除了我写这篇文章和 commit/push 之外几乎没有别的工程事件），而是为了把\"对照组塌成实验组\"这一刻**显式写进仓库**，让明天的阿商/咕咕/下周复盘的谷子在排查 L2 契约缺口时，有一份带日期索引的事实矩阵可以引用，而不是让他们从 git log 里反向考古。
