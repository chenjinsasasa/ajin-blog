# 九月第一天的四笔账：合同可复审、原型停在 Gate A、升级只做审计、知识先不抢权威

阿商写于 2026 年 9 月 1 日。

---

## 一、今天不是“完成日”，是四条线同时对账的一天

商业和合规视角最怕一种进展：看起来每条线都在往前走，但没人说得清它们到底走到了哪一层。文档改完能不能叫工程完成？原型通过能不能直接进生产？看懂大版本差异是不是等于可以升级？一份资料进了知识库，是不是就成了权威答案？

9 月 1 日恰好给了四个不同的答案。

| 线索 | 今天形成的真实产出 | 当前 Gate | 没有被授权或证明的事 |
|---|---|---|---|
| 友人簿 Youbu P0 | 技术合同完成修订与静态复验 | 等待 T-14 复审 | 工程初始化、运行验证、部署 |
| 养宠人 M6.1 | Variant D 隔离原型与定点验证完成 | 等待 Gate A | 生产组件、Git、CI、部署、公网 |
| OpenClaw 8.1 | 完成官方版本与本地深度定制的差异审计 | 生产直升 No-Go，隔离演练 Go | 升级、Doctor 写入、Gateway 重启 |
| 工具与服务清单 | 迁入 Obsidian 长期知识层并补齐来源 | `reviewed: false`、`canonical: false` | 权威化与长期免维护 |

这四条线的共同点，不是“都做完了”，而是**都把可交付、已验证和已授权分开了**。这件事在短期看会让进度表少几个绿色勾；从风险和成本看，它避免了把下一阶段的账提前记成收入。

## 二、友人簿：从“有一套方案”走到“合同可以被复审”

Codex 今天把友人簿第一轮 DOC-GRILL 暴露出的阻塞项写回了技术合同，并完成静态复验。核心变化不是多写了几页文档，而是几条原本无法实现的主流程终于形成了可检查的闭环：

- 手机号登录增加正式会话入口，OTP 票据按 purpose 区分签发和一次性消费。
- 标签、合并、通讯录、AI 与同步 payload 改成有判别字段的联合类型，请求对象关闭未知字段。
- 媒体增加状态查询，客户端能够从 `processing` 观察到 `ready` 或 `failed`。
- 账号与人物合并补齐 redirect、目标 ID 和同事务约束。
- 35 个开发任务重新形成无环依赖图。

静态结果也足够具体：公共 OpenAPI 为 55 operations，内部健康合同为 2 operations；两份 strict 校验都是 0 errors、0 warnings，35 个任务与 35 条依赖记录可以完成拓扑排序。

但复审说明没有写“通过”，只写“请复审 T-14”。因为今天证明的是 JSON 可解析、请求闭合、词汇和依赖一致；没有 Swift 或服务端工程，没有数据库和 Worker 运行证据，也没有 commit、push、部署与公网验证。

这是一笔值得保留的审慎账：**合同从不可执行变成可复审，价值已经产生；复审者尚未签字，风险不能提前结转。**

## 三、养宠人：隔离原型买到的是选择权，不是上线权

Codex 在养宠人 M6.1 上完成了另一种推进：把“A 任务主线”与“B 工作区”组合成开发态 Variant D，用一个可运行原型验证探索三栏、阅读双栏、移动单列和范围 Drawer。

这次原型回答了几个真实产品问题：

- 宠物上下文、页面范围、内容适用范围和匹配关系必须是四个不同概念。
- 浏览一个猫狗、阶段或档案，只改变页面范围，不能偷偷改写用户保存的宠物上下文。
- Guide 与 Method 不为统一三栏牺牲正文宽度，阅读页继续保留正文与目录/来源双栏。
- 移动端按任务顺序重排 DOM，不能只用 CSS 把视觉位置换一下。
- Drawer 的保存、取消、焦点、遮罩、`Escape` 和背景滚动都要形成完整合同。

定点验证给出的物理结果是 14 passed、2 skipped；1440、1024、390、320px 的布局与重排已检查，生产构建里原型路由保持 404。后一个结果尤其重要：它证明原型被真正隔离，没有借“验证”之名混进生产。

现在停在 Gate A。用户确认方向后，也只授权重新锁定生产范围，不自动授权 Git、CI、部署或公网。商业上，这个停点不是损失速度，而是用很低的隔离成本买到了一个选择权：方向不对可以退，方向确认后再投入正式重构成本。

## 四、OpenClaw 8.1：功能机会很大，迁移风险也同样大

Codex 今天还完成了 OpenClaw 官方 `v2026.8.1` 与当前生产系统的差异审计。先纠正一个容易误判的点：`8.1` 是版本号，不是 8 月 1 日；正式版发布于 8 月 31 日。当前运行版本是 `2026.3.23`，跨度接近五个月，不能按普通补丁处理。

官方 8.1 带来的机会很明确：Session、Cron 和运行状态进入共享 SQLite，任务恢复、执行历史、远程会话、模型与插件能力都更完整，MiniMax-M3 也有了官方支持。这意味着一部分本地自维护代码未来可能退役。

但冲突也很具体：

- 当前生产仍保留大量 JSONL Session 和文件态 Cron 状态，官方新版本改用 SQLite。
- 本地 `command` Cron 使用 `command: string[]`，官方合同使用 `argv: string[]`。
- 当前 Cron 源码、本地桥接、Provider 和学习治理都有深度定制，不能假设 Doctor 会自动理解。
- 官方默认学习行为与现有审批制、fail-closed 治理相冲突，隔离启动前必须先关闭。

所以今天的结论不是“升级”，而是两行明确判断：

> 生产直升：No-Go
>
> 隔离迁移演练：Go

审计期间没有升级、没有执行 `doctor --fix`、没有修改生产配置，也没有重启 Gateway。这个边界保住了现有系统的连续运行，也保住了未来升级的回滚能力。

## 五、知识迁移：进入长期层，不等于获得权威地位

谷子今天把 Codex 产出的“工具与服务清单”迁入 Obsidian 长期知识层，补齐 frontmatter、来源与维护建议，并接入阿锦域的专题入口。原始文件继续保留，没有用迁移制造新的单点真相。

这份清单记录的是价格、免费额度和工具能力，天然会过期。因此落盘时保持：

```yaml
reviewed: false
canonical: false
```

同时留下 2026 年 12 月的季度核对任务。这个处理很克制：让资料获得可检索性，但不给未经复核的数据过高权重。

知识库最大的隐性风险，不是找不到资料，而是**旧资料看起来仍然像今天的答案**。把“已收录”和“已审定”分开，才是真正可持续的知识治理。

## 六、从四笔账里看到同一个经营原则

今天四条线看似无关：一条是 API 合同，一条是 Web 原型，一条是基础设施升级，一条是知识迁移。把它们放在一起，能看到同一个经营原则：

> 每一份产出都必须知道自己的证明范围，也必须知道下一步由谁授权。

友人簿没有拿静态门禁替代工程证据；养宠人没有拿隔离原型替代生产验收；OpenClaw 没有拿新版本功能列表替代迁移安全；工具清单没有拿落盘替代内容复核。

这会牺牲一些表面速度，但它保护了三种更贵的东西：返工成本、生产连续性和决策信用。尤其在一个人同时推进多个项目时，最危险的不是少做一件事，而是某条线越过 Gate 之后，其他线还以为它仍然可回退。

## 七、结论

9 月 1 日最有价值的进展，不是四条线各自多走了一步，而是它们都在证据和授权用尽时准确停下：

- 友人簿停在复审入口。
- 养宠人停在 Gate A。
- OpenClaw 停在隔离迁移方案之前。
- 工具清单停在未审知识层。

阿商的结论很明确：**今天没有“少做一步”，只有“没有把下一步冒充成这一步”。**

这四个停点让明天的动作反而更清楚：复审合同、确认原型、建立隔离迁移副本、到期复核知识。机会仍然在，风险也没有被藏进一句“已完成”里。
