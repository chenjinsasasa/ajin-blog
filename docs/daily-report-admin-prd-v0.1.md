## 1. 定位与范围

[已知] 建设 ajin-blog 自己的独立后台和数据库，用于观测、管理每天日报的阶段、完成进度和卡点，不整合为 OpenClaw Dashboard 的页面。

[建议] 首版按单管理员、需要登录设计。核心体验：30 秒内看懂今日状态，遇到阻塞能找到原因、证据及下一步操作。后台管理业务，现有项目程序执行业务，OpenClaw 保持调度和模型配置职责。

V0.1 包含日报总览、日报详情、异常待办、运行与产物历史、受控重试和补跑、操作审计。正文与图片继续由现有文件和 Git 管理，数据库保存流程数据、版本引用和必要的脱敏预览数据。

本版不包含在线编辑文章、任意改写状态、绕过审稿/封面门禁、模型配置编辑、调度配置编辑、多用户角色体系及新通知渠道。预留这些需求，不把它们加入本轮实施范围。

## 3. 用户与主要动线

[建议] 用户为博客所有者，通常每天查看一次，失败时进入详情处理。

1. 登录后台，在总览看到今日计划和未完成的历史日报。
2. 点击一条日报，查看阶段时间线、最后活动时间、产物和错误摘要。
3. 对可恢复的问题查看恢复范围，提交重试或补跑。
4. 页面显示“已排队”，执行器实际接收后显示“进行中”。
5. 返回查看结果；完整验证通过后显示“已发布”，失败则保留本次证据及下一步。

## 4. 页面要求

### 4.1 日报总览

- 顶部展示今日业务日期、计划触发时间、当前状态、执行器在线情况、数据更新时间。
- 显著展示仍未完成的前一日任务，避免跨午夜后被今日空记录遮住。
- 列表默认最近 30 个业务日，支持日期、结果、异常类型筛选及分页。
- 每行：日期、文章标题（未生成则为空态）、状态、当前阶段、阶段耗时、最后活动、问题摘要。
- 无进程活动不能仅由耗时推断；展示的是最后事件时间还是 worker 心跳必须明确区分。
- 不显示缺乏依据的预计完成时间或百分比；采用阶段完成情况。
- 首次接入无数据、计划尚未到时、无公开素材、采集离线须呈现不同空态。

### 4.2 日报详情

- 摘要：业务日期、整体状态、当前卡点、建议动作、正文标题、最终访问地址。
- 阶段时间线：开始/结束、耗时、状态、尝试次数、错误代码和中文解释。
- 产物区域：正文只读预览、封面预览、审稿意见、简报摘要；绑定当前运行与内容版本。
- 发布阶段展开：项目校验、提交、各远端推送、轮值处理、CI/部署、公网检查、终态回执。执行顺序以程序为准。
- 每次运行展示独立记录及触发来源；恢复可以关联原运行，不能覆盖原失败。
- 支持查看脱敏证据与复制 run_id；缺失、过期、哈希不匹配的证据明确标识。
- 已发布结果显示当时验证时间；后续站点故障另列健康异常，不抹去历史发布事实。

### 4.3 异常待办

| 异常 | 判断依据 | 默认处理 |
| --- | --- | --- |
| 到时未启动 | 到达计划时间与宽限期，且未观察到目标日期运行 | 核查调度与执行器；符合条件后补跑 |
| 阶段失败 | 绑定本次尝试的失败事件或有效失败回执 | 展示原因和可恢复范围 |
| 阶段超时 | 执行器明确返回 timeout | 保留输出和进程处置证据，再判断能否重试 |
| 长时间无更新 | 超过阶段观察阈值，缺少完成证据 | 标为状态待核实，不自动重跑 |
| 执行器离线 | 心跳超过阈值 | 标记数据滞后，禁止产生并发恢复 |
| 证据冲突 | 数据库、ledger 或回执不一致 | 标为状态待核实，进入对账 |
| 待人工处理 | 审稿预算耗尽、视觉未通过或恢复条件不足等明确事件 | 呈现处理建议，不提供绕过按钮 |

待办可记录意见和“处理中”标记；只有新证据证明恢复或终态成立才关闭业务异常。备注不能把失败改成成功。

## 5. 状态合同

### 5.1 日报结果与观测健康分开

| 业务状态 | 定义 |
| --- | --- |
| 未开始 | 已有预期日报记录，尚无有效运行；计划到时与否另行标记 |
| 已排队 | 后台请求已持久化，执行器尚未开始 |
| 进行中 | 有绑定运行的活动证据，尚未终止 |
| 已阻塞 | 明确失败或需人工处置，不能自动继续 |
| 已发布 | 通过现有终态验证并绑定文章、封面与发布版本 |
| 已跳过 | 有有效的无公开素材终态回执，未执行发布 |
| 状态待核实 | 当前证据不足或矛盾，不能确认业务状态 |

另存观测健康：正常、数据滞后、执行器离线、证据冲突。仅采集断线时保留最后确认状态和确认时间，界面加滞后标记，不篡改已发布历史。

### 5.2 阶段与转换

展示阶段为素材准备、正文写作、事实审稿、修订复审、封面简报、封面生成、视觉验收、发布验证。修订复审未触发时标“不适用”，不能伪造完成记录。

阶段尝试状态：未开始 → 进行中 → 成功 / 失败 / 跳过。失败后恢复建立新尝试，原尝试不可被覆盖。阻塞重试、人工补跑进入新运行或关联恢复运行；任何恢复都必须保留原始 guard 身份关系。

已有代码中的 `step completed` 只证明调用返回：只有后续阶段启动或该节点的业务结果事件证明门禁已通过时，阶段时间线才显示“已完成”与成功图标；只有调用返回但缺少后续验收证据时仍显示“调用已返回”。`workflow needs_attention` 是运行控制事件，不作为独立业务阶段展示；须按受控失败原因或最后一个未完成的阶段尝试映射到具体节点。调用返回后的业务合同校验失败标为“验收未通过”。审稿 PASS、视觉 PASS、发布成功仍必须分别经过其业务合同校验，不能由 completed 一词推导。

日报业务日期在创建时固定为 Asia/Shanghai 日期；所有事件时间保存带时区时间戳。跨午夜继续写入原日期。首页不得以服务器 UTC 日期替代业务日期。

### 5.3 预期记录与阈值

- 后台独立的日历对账任务建立预期记录，不依赖生产任务成功启动。服务停机恢复后补齐启用日期以来的缺失记录。
- 计划时间来自已配置调度的只读快照，保存时区、配置版本与生效时间；变更不回写历史预期。
- 调度明确关闭时显示“计划已停用”，不自动当作漏跑。
- [建议默认值] 页面刷新 15 秒，worker 心跳 30 秒，90 秒未收到心跳标离线；计划触发宽限期 10 分钟。以上均为待实测参数，不是现有能力或运行事实。
- 阶段 timeout 以执行器实际预算为准；发现外层任务期限小于内层预算时记录配置问题，不能自行增加预算。

## 6. 数据模型与事实归属

| 对象 | 关键字段 / 约束 |
| --- | --- |
| daily_reports | id、business_date（唯一）、timezone、scheduled_at、schedule_version、result、current_run_id、post_ref、last_verified_at |
| runs | id、report_id、guard_run_id、parent_run_id、trigger_source、started_at、ended_at、status、original_failure_ref |
| stage_attempts | run_id、stage_key、attempt_no、status、started_at、ended_at、error_code、reason；三元组唯一 |
| events | producer_id、event_id、run_id、sequence、occurred_at、received_at、type、payload_hash；producer/event 唯一 |
| artifacts | run_id、stage_attempt_id、type、version、content_hash、storage_ref、verification_status |
| commands | id、report_id、action、idempotency_key、expected_version、status、requested_by、lease、result_ref |
| audit_logs | actor、command_id、action、timestamp、result、reason；追加记录 |
| worker_health | worker_id、last_seen_at、active_run_id、capabilities、version |

- 数据库是后台查询、命令及审计的持久化存储；V0.1 发布终态仍以现有受验证的 ledger/receipt 为依据，数据库保存其可重建投影。
- 执行器拥有互斥、审稿预算、文件安装、Git 和发布状态转换权。后台不直接写 ledger、清理 pending 或改正文。
- 事件按身份去重，乱序到达不得倒退投影；无法确定顺序时对账。重复读取同一 state.json 不能重复创建运行。
- 已有历史数据只导入能证明的事实；没有阶段时间戳就标未记录，不能倒推虚假耗时。
- 正文和图片的预览必须对应产物哈希；云端部署时本机文件路径不是可访问 URL，需经受控产物接口同步或读取。
- 数据库故障时，现有自动链路继续按原本的持久化门禁工作，观测事件本地缓存后重放；后台管理命令无法持久化则拒绝接收。不得声称无日志的执行成功。

## 7. 管理操作合同

### 7.1 重试阶段

界面动作名为“重试阶段”，先展示本次恢复的起点、将复用的产物及可能推进到发布的范围，再由用户提交。命令明确记录是否包含后续发布，不能把仅重做封面静默扩大为提交推送。

服务端与 worker 双重检查：身份授权、运行版本未变化、无在途执行、旧进程已结束、上游哈希有效、审稿预算未重置、该阶段支持恢复。界面能力由执行器返回，不根据前端状态自行猜测。

V0.1 优先实现封面简报、封面生成、视觉验收及发布验证的受控恢复；所有入口仍经过现有合同。正文或审稿失败先展示明确阻塞与人工处理路径；若执行器不支持恢复，按钮禁用并说明原因。

提交前先检查已有 commit、远端 SHA 和部署结果；已有发布副作用时先对账，不能重复生成、提交、推送或推进轮值。恢复事件关联原始失败回执，按现有 guard 恢复合同保留身份，不能简单换 run_id 绕过 pending。

### 7.2 发起补跑

仅针对明确业务日期；服务端拒绝未来日期、有效已发布/已跳过日期和有在途运行的日期。历史素材不足时按现有规则跳过，不拼造素材。

补跑通过完整的现有预检与执行链路；记录来源为 manual_backfill，不能作为自然调度成功证据。显示“执行完整生产与发布流程”及目标日期后提交。

### 7.3 命令生命周期

queued → claimed → running → succeeded / failed / rejected；执行中失联进入 uncertain，先核对进程与副作用再决定结算。重复点击使用相同幂等键返回同一命令；不同键也须按日报和在途运行互斥。

领取租约过期不能直接重复执行具有外部副作用的命令。入队未领取命令建议 30 分钟过期，避免本机离线数小时后突然发布；到期显示需重新发起。数据库记录的 succeeded 必须有实际执行结果。

## 8. 部署与访问方案

【本次更新】用户已明确首版本机使用，远程访问不纳入 V0.1。

### 8.1 本机结构

[建议] 采用独立后台服务 + 本机 SQLite 数据库 + 本机执行适配器。SQLite 为技术方案候选基线，驱动、事务和并发方式在实现前验证。

```text
本机浏览器
  → ajin-blog 管理后台（仅监听 127.0.0.1）
    → 本机数据库：日报、运行、事件、命令、审计
    → 本机执行适配器：读取证据、领取受控命令
      → 现有日报执行程序与发布门禁
OpenClaw → 现有定时任务 → 同一执行程序
```

- 后台具有独立启动入口与运行配置；公开博客继续现有部署。管理 API、私有产物与数据库不进入公开网站的部署产物。
- 数据库放在 Git 工作区之外的专用持久化数据目录；具体路径、端口在技术方案中确定。禁止把运行数据库或备份提交到仓库。
- 页面关闭不应停止已提交任务；后台服务与执行适配器的生命周期不依赖浏览器页面。
- 后台读取现有运行证据，管理动作通过白名单命令进入现有执行链路，不提供任意 shell 执行接口。
- 日历对账与 worker 心跳都在本机运行。本机休眠或关机时，后台同样不可用，不能提供实时离线告警；恢复后补齐预期日期，并显示观测中断区间。
- 后台仍在运行而执行适配器停止时，可通过心跳检测离线。无历史证据时无法精确还原整机停机时间，必须标记未知区间。
- 服务重启先对账在途进程、命令和发布副作用，再恢复消费；不能启动即重跑未完成日报。

### 8.2 访问与数据保护

[建议] 保留单管理员服务端会话。页面、读写 API 和私有产物统一验证；写操作具备 CSRF 防护、幂等与审计。仅监听回环地址，首版不配置公网域名、局域网访问或云端数据库。

日志与预览去除密钥和非公开素材。数据库须有一致性备份与恢复验证；备份方式应适配所选数据库事务模式，不能直接复制运行中的文件后宣称备份有效。原始文章与凭证不写入事件 payload。

### 8.3 技术方案待验证项

1. 独立服务的工程位置、启动入口、端口、持久化数据目录及日志目录。
2. SQLite 驱动与事务策略，事件写入与命令领取的并发控制，迁移和备份恢复方式。
3. 现有 journal / ledger / receipt 的只读适配与新增子阶段事件接口。
4. 后台与执行适配器的启动、停止及本机登录后运行方式；实施时不擅自修改系统休眠设置。
5. 会话认证与仅本机访问的检查，确保公开博客构建不携带管理数据或管理接口。

## 9. 实施切片与验收

### M1：可观测

建立数据库和只读适配器，导入可验证历史；独立建立预期日报；拆出封面及发布子阶段事件；实现总览、详情、异常页与鉴权。此阶段明确标为只读版，不算完整 V0.1 管理能力交付。

### M2：可恢复

实现命令队列、幂等、互斥、能力发现、受控恢复及补跑；验证过期命令、崩溃重启和已有发布副作用处理。复用既有门禁与恢复入口，需要补齐的能力单独测试。

### M3：真实链路验收

把实现、测试、部署、真实运行分别报告。隔离测试可使用故障注入；生产验收不通过清 ledger、制造未来日期或重复发布来构造成功。

| 场景 | 通过标准 |
| --- | --- |
| 正常生成 | 阶段与真实执行对应；操作员 30 秒内能判断进度 |
| cron 未触发 | 到期宽限后仍存在该日日报记录，显示未启动及证据时间 |
| 无公开素材 | 有效 skip 回执显示已跳过，不生成文章或图片 |
| 审稿需修订 | 修订与复审展开；不超过原审稿预算 |
| 生图失败 | 准确落在封面阶段，保留错误；不替换模型或来源 |
| 视觉失败 | 阻止发布；不提供绕过审核操作 |
| 执行适配器失联 | 后台在线时在设定阈值内显示离线及最后确认时间，不伪造业务失败 |
| 整机休眠或关机 | 恢复后显示观测中断、补齐预期日报并对账；不声称停机期间实时监测 |
| 跨午夜 | 昨日日报继续归属昨日，今日计划单独展示 |
| 重复点击/重复事件 | 至多一次有效命令与副作用，事件不重复计数 |
| 执行中崩溃 | 命令变为待核实并对账，不能租约一过期就重复发布 |
| 已提交但 CI 失败 | 保留 commit 和远端证据，恢复不重复提交或推进轮值 |
| 回执或哈希冲突 | 不显示已发布，给出明确待核实原因 |
| 人工补跑成功 | 显示业务成功及人工来源，原自动失败仍可查看 |
| 未登录/越权请求 | 页面、API、私有产物及命令均拒绝访问 |
| 数据库恢复 | 能恢复运行与审计记录，并从证据对账，无重复操作 |

[建议指标] 在线情况下阶段变化 30 秒内可见；实际性能和刷新频率通过端到端测量确认。真实自然调度成功与人工验收分开记录，不能互相替代。
